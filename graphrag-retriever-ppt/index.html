GraphRAG Retriever Review

轻量 GraphRAG
检索器总结

面向微信群聊关系图谱的命令行检索层：读取 graph_state.pkl， 将人、路径、社区三类图结构召回为可读上下文，供人工查看或喂给 LLM 二次生成。

实体检索关系路径社区摘要CLI / REPL

01 · 文件定位

它不是构图脚本，而是图谱检索入口

Input

graph_state.pkl

由 graphrag_analysis.py 预先生成，包含图、昵称映射、社区划分、节点统计等状态。

Core

networkx 图检索

在已有关系图 G 上读取节点、边权、社区成员和路径，不重新解析聊天记录。

Output

上下文块

输出结构化文本：个人关系、两人桥梁、社区成员与摘要，可直接作为 Prompt Context。

02 · 代码结构

单文件，按检索动作分层

0load_state读取 graph_state.pkl，缺失时提示先运行分析脚本。
1resolve_user按精确昵称或子串做实体链接，多候选时要求用户细化。
2query_person以人为中心召回强关系、互动统计和社区上下文。
3query_path查询两人之间 Top-K 最强连接路径。
4query_community汇总社区成员、内部互动和模板摘要。

03 · GraphRAG 在这里如何实现

核心是“图谱召回”，不是大模型生成

这个文件把 GraphRAG 拆成一个轻量闭环：先从持久化图状态中定位实体， 再沿图结构召回关系证据，最后把证据整理成可读上下文。

  • 实体：微信群用户，使用 wxid 作为稳定节点 ID。
  • 关系：互动边，边上保存 weight、mention、quote、pat、adjacent。
  • 社区：Louvain 结果已写入 partition、comm_members、comm_cores。
  • 回答：当前使用模板化输出；LLM 可接在输出之后做自然语言总结。

GraphRAG 映射关系

Query人名、两人关系、社区 ID
Retrieve节点邻居、最强路径、社区内部边
Context结构化关系证据和统计摘要
Generate脚本内模板生成，或交给 LLM 二次生成

04 · 三类检索能力

从点、线、群三个视角召回上下文

命令解决的问题关键实现输出内容
person 某个人在群里的社交位置是什么？ 读取节点属性、加权度、邻居边权和所属社区。 发言量、@/引用统计、Top-K 强关系、同社区成员。
path 两个人之间通过谁连接？ 复制图，将 distance = 1 / weight，用 shortest_simple_paths 求强路径。 跳数、最弱一跳、累计权重、每条边的互动明细。
community 一个社区内部是谁主导、怎么互动？ 按加权度排名成员，统计社区内边的互动类型分布。 核心人物、成员榜、内部 Top5 强关系、模板摘要。

05 · 关键算法细节

把“关系强度”转成可检索的图信号

实体链接

resolve_user 先精确匹配昵称，再做子串匹配。多候选不盲选，返回候选列表，降低错连实体的风险。

强关系排序

query_person 按边上的 weight 降序排列邻居，所以输出的是互动证据最强的一跳关系。

最强路径

路径搜索不是按跳数最少，而是用 1/weight 当距离，优先选择由强边组成的路径。

社区回答

社区摘要通过统计主导互动类型、核心人物和内部边数量生成，属于无需 LLM 的模板版 GraphRAG 回答。

06 · 当前价值与限制

工程上已经可用，但仍是轻量版

价值

  • 本地运行，不依赖在线模型。
  • 输出可解释，每条关系都有权重和互动构成。
  • 检索入口清晰，便于接入后续问答系统。
  • 适合快速探索群聊社交结构。

限制

  • 没有语义向量检索，主要依赖结构关系。
  • 回答生成是模板化的，表达能力有限。
  • 实体消歧只基于昵称字符串，缺少上下文判断。
  • 图状态是 pickle 快照，跨版本和可审计性一般。

08 · 结论

这个文件把聊天关系图
变成了可查询的 RAG 上下文

graphrag_retriever.py 的实现重点是稳定、可解释、低依赖： 通过实体解析、图路径搜索和社区统计，把复杂群聊关系压缩成面向问答的上下文块。 下一阶段重点是学习 LightRAG，并评估是否加入语义检索与自动生成能力。
