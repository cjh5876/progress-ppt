CODE READING REPORT

LightRAG 与 GraphRAG
差别在哪里？

基于 paper_lightrag.py 的数据结构、索引流程与检索代码，分析两类组件的用途、侧重点和适用场景。

核心判断：两者都使用知识图谱，但优化目标不同。

01 · 先看代码实现

paper_lightrag.py 实际构建了什么？

原始证据Chunk按时间间隔和消息数切分聊天原文。
图节点Entity用户与主题词，带描述、来源和 rank。
图边Relationmention、quote、adjacent、co_topic。
高层摘要CommunityLouvain 聚类后的社区报告。
检索入口Vector Index四类对象分别建立向量索引。
chunks → entities → relations → graph; communities; vector_indexes

02 · LightRAG 的代码证据

关键不是“只有图”，而是“图 + 多层证据”

DATA MODEL

四类对象都能被检索

build_vector_indexes() 为 chunk、entity、relation、community 分别生成向量矩阵；查询不必只命中文本块。

DUAL LEVEL

局部与全局并行

retrieve() 同时搜索低层实体/关系和高层社区报告，再收集关联原文作为证据。

HYBRID

结构检索与语义检索混合

普通问题走向量相似度；关系问题改用实体 rank 和关系 weight，避免“谁和谁最密切”被文本相似度带偏。

INCREMENTAL

稳定 hash 复用 chunk

build_indexes(previous_state=...) 按 chunk hash 复用未变化内容，体现轻量、可增量更新的工程取向。

03 · 检索路径

同一个问题，LightRAG 会走两条路

LOCAL / LOW-LEVEL

回答“具体是谁、发生了什么关系”

  • 向量命中实体与关系。
  • 扩展一跳图邻域。
  • 回溯实体和关系的 source_chunks。
  • 关系问题按 weight 强制重排。
GLOBAL / HIGH-LEVEL

回答“整体上有哪些主题和群体”

  • 向量命中 community report。
  • 读取社区的核心实体。
  • 补充相关 chunk 作为背景。
  • 适合概览、主题和群体画像。
mode = local   → 低层图证据; mode = global → 社区级证据; mode = hybrid → 两者合并

04 · GraphRAG 的典型侧重点

GraphRAG 更强调“先建好图，再做全局组织”

GRAPH-FIRST

图是主索引

实体、关系、社区和层级摘要通常由离线流程集中构建，查询围绕图结构展开。

GLOBAL SYNTHESIS

社区摘要是主武器

对大规模语料的跨文档主题进行聚合，适合回答“整体有哪些观点/主题”。

QUALITY OF REPORT

重视摘要质量

社区报告通常需要更强的抽取、归纳和 LLM 生成能力，换取全局回答的完整度。

注意：这里说的是典型 GraphRAG 方法论。具体项目可能同时加入向量检索、局部邻域和混合策略。

05 · 直接对比

差异不在“用不用图”，而在“图服务什么目标”

维度LightRAGGraphRAG
首要目标低成本、快速、灵活地组合局部与全局证据把大语料组织成可解释的全局知识结构
检索入口chunk / entity / relation / community 多入口以图、社区和层级摘要为核心
查询粒度局部实体关系与全局主题都强调更擅长跨文档、跨实体的全局综合
更新方式适合增量插入，hash 可复用 chunk图和社区摘要变更后，重建成本通常更明显
工程取舍轻量、离线可跑、模块可替换建设成本更高，但全局摘要能力更强

06 · 用途分工

从问题类型看，谁更适合什么？

更适合 LightRAG

关系密集、变化频繁、需要追溯原文

  • “谁和谁互动最密切？”
  • “这个用户和哪些主题相关？”
  • “这条关系来自哪些消息？”
  • 在线知识库的增量更新和快速试验。
更适合 GraphRAG

语料规模大、需要全局综合和社区洞察

  • “整个资料库有哪些主要主题？”
  • “不同群体的观点如何分化？”
  • “跨文档的共同结论是什么？”
  • 报告生成、知识地图和宏观分析。

07 · 代码里的工程取舍

paper_lightrag.py 选择了“可控、可解释、可离线”

可控

关系类型和权重显式定义：mention=3、quote=4、adjacent=1、co_topic=0.6，排序逻辑可检查。

可解释

每个 entity、relation、community 都保存 source_chunks，检索结果可以回到原始聊天片段。

可离线

向量使用本地字符 n-gram hashing，不依赖外部 embedding API，适合原型和隐私敏感数据。

代价：字符 n-gram 语义能力有限，社区摘要也是模板化文本，不能等同于完整的生产级 GraphRAG。

08 · 边界与风险

读代码时必须保留的三个判断

01

实现不等于论文全貌

文件标题和注释说明了 LightRAG 形状，但它使用的是本地 hashed embedding，是可运行的简化实现。

02

关系抽取是规则驱动

关系主要来自 @ 提及、引用、相邻消息和共现主题，不是完整的开放域语义关系抽取。

03

GraphRAG 不是单一产品

GraphRAG 可以包含局部检索、向量检索和 LLM 生成；比较时要区分方法论、实现和产品封装。

09 · 结论

一句话总结

LightRAG 侧重“用轻量图结构把局部关系、全局社区和原文证据灵活拼起来”；GraphRAG 侧重“用分层图与社区摘要理解大规模语料的全局结构”。

选择 LightRAG

需要快速落地、增量更新、关系可追溯，且希望 local/global/hybrid 由查询决定。

选择 GraphRAG

需要面向大语料做全局主题归纳、群体分析和高质量报告生成。

最实际的方案：保留 GraphRAG 的社区级组织能力，吸收 LightRAG 的多入口检索和增量更新。
